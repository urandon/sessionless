# YDB physical partitioning contract

This document is the executable companion to the architecture decision in
[design issue #1](https://gitcode.com/urandon/sessionless/issues/1#tid-182320319).
It records which primary-key ranges carry each operational workload and how
the repository detects drift.

YDB row tables are range-partitioned by the lexicographically ordered composite
primary key. Size-based splitting is enabled by default, while load-based
splitting is disabled by default. One partition is hosted by one server and can
use at most one CPU core for updates. A correct primary key can therefore still
be a scale bottleneck.

Primary references:

- [YDB row-table partitioning](https://ydb.tech/docs/en/concepts/datamodel/table#partitioning_row_table);
- [selecting a row-table primary key](https://ydb.tech/docs/en/dev/primary-key/row-oriented);
- [YDB `CREATE TABLE` partition settings](https://ydb.tech/docs/en/yql/reference/syntax/create_table/).

## Identifier contract

Production operational IDs are generated by `internal/idgen` from 128 random
bits and a fixed kind prefix. They contain no timestamp, sequence, tenant
payload, or frontend identifier. The first symbol after the prefix therefore
has 32-way Base32 entropy instead of a moving lexicographic edge.

This applies to tenant, actor, conversation, subscription, run, attempt, lease,
checkpoint, quota, usage, manifest, outbox, delivery, and queue-message IDs.
Timestamps used for ordering remain separate columns.

Test-only sequence IDs stay in `internal/testkit`; they must never be wired into
a production adapter.

The four v2 tables use SHA-256 bucket derivation from the immutable object ID:

```text
bucket_v1(id) = big_endian_uint32(sha256(id)[0:4]) mod 16
```

This distributes one elephant tenant as well as many small tenants. Each table
starts with 16 explicit key ranges (`0` through `15`), enables size and load
partitioning, keeps at least 16 partitions, allows growth to 256, and uses a
512 MB size target. Global consumers enumerate the fixed bucket list and issue
one bounded time-prefix query per bucket. The tenant remains in every row and
is validated before mutation; the bucket is not an authorization boundary.

The four legacy tenant-first ready/expiry tables remain during the compatibility
window. New code dual-writes legacy and v2 rows. Serving code must use the v2
layout for global traversal; legacy scans are allowed only in the backfill
command.

## Inspection

With local YDB running:

```sh
make migrate-local
make partition-status
```

`schema-inspect` emits machine-readable JSON containing the expected and actual
primary keys, auto-partition settings, current partition count, row estimate,
and contract violations for all 22 logical tables. It exits non-zero on drift.

YDB Local proves key shape, deterministic bucket targeting, bounded fan-out,
and initial partition settings. It does not prove Yandex Serverless throughput,
RU consumption, or split/merge latency.

## Expand, backfill, cut over, contract

1. **Expand:** apply migrations `00023` through `00038`. They create the four
   v2 tables and enable explicit load-aware settings on expected high-write
   tables. No primary key is changed in place.
2. **Dual write:** deploy the control revision that writes both legacy and v2
   ready/expiry rows. The previous revision remains compatible because the
   legacy tables are untouched.
3. **Backfill:** run `make partition-backfill`. The command scans only the four
   legacy tables and idempotently upserts v2 rows. Rerunning is safe. Use
   `.build/bin/schema-backfill --dry-run` to report row counts without writes.
4. **Verify:** compare legacy/v2 logical counts, run `make partition-status`,
   and exercise duplicate ingress, lease renewal, quota transitions, dispatch,
   and delivery retry.
5. **Cut over:** deploy bounded-bucket readers from the scheduler/reconciler
   task and confirm no legacy-only writes for at least one maximum lease/retry
   window.
6. **Contract:** stop legacy dual writes and drop legacy tables only through a
   later reviewed migration. No automatic down migration is provided.

The current project has no cloud production data. This procedure is still
executable so cloud-dev and later environments do not invent a different
primary-key migration protocol.

## Structural workloads and cloud gate

Deterministic tests cover:

- 65,536 monotonic IDs from one elephant tenant;
- high-entropy operational ID generation;
- every bucket derivation golden vector;
- exactly 16 bounded ready/expiry targets;
- migration repeatability, v1/v2 dual writes, and bucketed expiry reads.

Cloud-dev and release-candidate tests must add:

- many evenly active tenants;
- one elephant tenant;
- monotonic burst writes for updates, checkpoints, ready/expiry, usage, and
  audit rows;
- per-shard CPU and overload status;
- partition count and headroom to the configured maximum;
- split/merge activity and retry latency;
- RU, throttling, retry rate, and cross-partition transaction count.

No local measurement is reported as a cloud throughput claim.
